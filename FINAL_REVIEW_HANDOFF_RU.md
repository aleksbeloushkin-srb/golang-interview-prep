## 3. Важная новая находка: syscall в Go 1.26

Это не косметическое переименование. Старая диаграмма `_Psyscall → handoff` больше не описывает обычный путь Go 1.26.1.

| Стадия | Go 1.25.0 | Go 1.26.1 |
|---|---|---|
| Обычный вход | G переходит в `_Gsyscall`, связь M–P снимается, P получает `_Psyscall` | G переходит в `_Gsyscall`; M и P могут оставаться связанными, P сохраняет `_Prunning` |
| Как распознать syscall для изъятия P | Старое состояние P и протокол retake | Проверка G и связей через `setBlockOnExitSyscall`; удержание scan-состояния не даёт G одновременно завершить выход |
| Передача P | Изъятие P по старому протоколу | `takeP`, затем `resume`, затем `handoffp` в рассмотренном пути retake |
| Заведомо блокирующий вход | Отдельный `entersyscallblock` | Тоже отдельный путь, отдающий P; его нельзя смешивать с обычным входом |
| Возврат | Нужно вернуть/получить P; иначе ожидание планирования | То же требование для обычного Go-кода, но другой внутренний протокол |

Наличие неиспользуемого слота также подтверждено в [теге 1.26.0](https://github.com/golang/go/blob/go1.26.0/src/runtime/runtime2.go). В 1.26.1 слот `_Psyscall_unused` прямо помечен как неиспользуемый в [runtime2.go](https://github.com/golang/go/blob/go1.26.1/src/runtime/runtime2.go). Сравнивать следует [proc.go 1.25.0](https://github.com/golang/go/blob/go1.25.0/src/runtime/proc.go) и [proc.go 1.26.1](https://github.com/golang/go/blob/go1.26.1/src/runtime/proc.go): `reentersyscall`, `entersyscallblock`, `exitsyscall`, `retake`, `setBlockOnExitSyscall`, `syscallingThread.takeP/resume`.

Схема описывает обычные runtime-aware пути. Она не является универсальной моделью `RawSyscall`, всех платформенных исключений, cgo callbacks и каждого GC-перехода. Cgo может вычислять в пользовательском C-коде, поэтому фраза «всегда застревает в ядре» тоже удалена.

## 4. Как теперь устроены схемы

**Sim1: 5 → 6 шагов.** Вычисление аргументов в G1 → подготовка G2 на g0 → сохранение стартового контекста → runnable/очередь → execute/gogo → goexit и завершение. На каждом шаге одинаковые опоры: кто исполняется, где стек, откуда продолжить. Текущая G на g0 и `M.curg` не смешаны. Размер стека и его сохранение после завершения не обещаются.

**Sim2: 4 → 8 шагов.** Источники работы; запрос вытеснения; безопасное переключение; очередь до перехвата; очередь после; сравнение syscall 1.25/1.26; возврат и необходимость P; поллируемая сеть. Это несколько подписанных сценариев. Только пары 2–3 и 4–5 составляют последовательные состояния; между независимыми примерами нет выдуманной непрерывной трассы.

Для перехвата используются A/B/C/D/E: было `[A B C D E]`, взяли `[A B C]`, осталось `[D E]`; у второго P очередь `[A B]`, C возвращена для исполнения. Проверка `2 + 2 + 1 = 5` помогает заметить потерянную или дублированную G. Это объяснение исходника при отсутствии конкурирующих изменений, не утверждение о гарантированном порядке приложения.

У неизменённых sim3–sim7 выполнена финальная сверка совместимости и браузерное прохождение всех шагов. Их тематические основания остаются в предыдущих отчётах; они не объявляются заново исследованными всеми инструментами только потому, что их открыли в браузере.

## 6. Версии: что ревьюеру нельзя склеивать

| Граница | Как учитывать |
|---|---|
| 1.17 и современный ABI | Архитектура и конкретный путь обязательны; внутренние регистры/раскладки не являются контрактом языка |
| 1.17 и современные начальные стеки | Не приписывать старому исходнику `startingStackSize` из нового; базовый stackMin не равен фактическому стеку каждой G |
| 1.18/1.19 | TryLock появился в 1.18; typed atomics и GOMEMLIMIT — в 1.19. Старые альтернативы отмечены в карточках |
| 1.20/1.21 | errors.Join — 1.20; clear и WithoutCancel — 1.21. Panic(nil) зависит от эффективной настройки panicnil |
| 1.22 | Семантика loop variables зависит от версии языка пакета, а не только установленного toolchain. `:=` и `=` различаются |
| 1.23 | Новая семантика timer channels зависит от main module/GODEBUG. Недостижимый таймер может собираться GC; это не ноль аллокаций. iter/unique тоже требуют новых версий |
| 1.24 | Swiss Tables стали стандартом; weak/AddCleanup уже появились. Не приписывать их появление 1.26 |
| 1.25 | WaitGroup.Go, стабильный synctest, FlightRecorder, container-aware defaults. Green Tea экспериментальный |
| 1.26 | Green Tea стандартный; старого переключателя noswissmap больше нет; изменён syscall-протокол; дополнительные детали WG.Go/cleanup сверяются по тегу |

**Исполнение новых fixtures выполнено Go 1.26.1 darwin/arm64.** Директива `go 1.17` в новом модуле фиксирует минимальную языковую/API-базу примеров, а не означает запуск toolchain 1.17. В этой порции старые toolchain не запускались. Сравнение реализации основано на tagged sources; переносить результат исполнения одной версии на другую безоговорочно нельзя.

Проверки предыдущих Go-модулей не запускались заново без изменения их примеров. Их фактические результаты сохранены в прежних отчётах. Проверка последних ссылок и всего UI не должна выдаваться за повторный запуск PostgreSQL, Linux cgroups или всех старых компиляторов.

## 8. Моё мнение о текущем результате

Теперь это пригодная проверенная база для разбора Go-механики и подготовки устных объяснений. Её сильные стороны — связность «вопрос → причина → код → схема → изменённое условие», EN/RU и явные границы утверждений. Самый существенный результат редакции — удаление ложной уверенности: фиксированных наносекунд, обязательных расписаний, жёсткого GOMEMLIMIT и универсальных рецептов.

Главное ограничение осталось продуктовым: пользователь может много читать глубокий runtime и мало писать код. Сайт пока не измеряет самостоятельное воспроизведение спустя дни, не хранит историю первой попытки и не проводит полноценное интервью. Правильный выбор из шести вариантов не равен способности вывести ответ без подсказки. Полная редакция этой базы сама по себе не закрывает HTTP/API/SQL-проект и прикладную разработку.

Не рекомендую сейчас переписывать сайт на фреймворк или переносить хостинг ради самого переноса. Следующая ценность — учебный маршрут, открытые задачи и журнал попыток. Для этого текущая статическая архитектура ещё подходит. Приоритет core/deep нужен, но не следует скрывать целиком CAS, каналы или c22 только из-за низкоуровневого продолжения ответа.

## 9. Запоминание: что есть и что добавлять

Весь текущий корпус получил практику воспроизведения и follow-up. Сначала короткая причинная модель, затем детализация. Схемы сохраняют одни обозначения между шагами; ответы не требуют угадывать смысл цвета. Примеры опор: «кто → где стек → откуда продолжить», «запрос → безопасная точка → переключение», «готовность ≠ исполнение», «ограничить операции ≠ ограничить потоки».

Исследовательская опора для дальнейшего учебного цикла — practice testing и distributed practice; обзор [Dunlosky et al., 2013](https://pubmed.ncbi.nlm.nih.gov/26173288/) оценивает их как широко полезные, а self-explanation/interleaving — более условно. Это основание проектировать проверяемый подход, а не обещание эффективности именно этого Go-сайта. Дополнительные исследования и оговорки собраны в [LEARNING_DESIGN_RU.md](LEARNING_DESIGN_RU.md).

Следующая реализация должна различать три события: **выполнил пункт плана**, **вспомнил технический ответ без подсказки**, **объяснил его по-английски**. Одна зелёная галочка не заменяет их все.

| Следующий элемент | Предлагаемое поведение | Проверка результата |
|---|---|---|
| Единица памяти | Маленький вопрос с критерием, а не весь длинный c22/c38 | Человек отвечает на один навык; обзорный ID сохраняется |
| Попытка | Записать content revision, время, язык, виденные подсказки, первую самооценку/результат | Повторное открытие ответа не превращается в первую правильную попытку |
| Интервалы | Расписание на основе попыток; экспорт/импорт до роста объёма истории | Просрочка, границы суток, смена зоны, закрытие вкладки, восстановление |
| Перенос | Менять условие: nil/closed, один/два sender, parent/child context, 1.25/1.26 | Ответ на новый код, а не повтор заученной строки |
| Английский | Технический ответ отдельно от оценки формулировки; сначала можно объяснить на RU | EN сохраняет условия и ограничения, а не лишь терминологию |
| Измерение | Самостоятельные ответы спустя 7/30 дней и на незнакомом примере | Это выбранные точки наблюдения, не универсальные интервалы обучения |

Цвета, размеры и движение служат читаемости и пониманию переходов. Нет основания обещать, что определённый цвет «внедрит материал в мозг». Не нужны наказания за пропуск серии или искусственное ощущение завершения после раскрытия ответа. Ошибка полезна, если после неё есть конкретная обратная связь и последующая самостоятельная попытка.

## 11. База данных, хостинг и будущий агент

Это варианты архитектуры для последующего решения, без выбора провайдера, тарифа или обещания сроков. Требования к синхронизации должны появиться до миграции.

| Вариант | Когда полезен | Дополнительная ответственность |
|---|---|---|
| GitHub Pages + локальные попытки/backup | Личная подготовка на одном устройстве, быстрый следующий этап | Миграция схемы данных, устойчивость storage, импорт/экспорт, восстановление занятия |
| Статический frontend + отдельный API и БД | Синхронизация устройств, история, серверный AI | Вход пользователя, проверки доступа, конфликты синхронизации, лимиты запросов, резервирование данных |
| Go-приложение, раздающее UI и API | Хочется единый deploy и практику разработки Go-сервиса | Эксплуатация, миграции, мониторинг, backup/restore; больший объём поддержки |

Минимальная логическая модель: content item/revision, exercise variant, attempt, review schedule, plan task completion. Начало с одного пользователя не оправдывает потерю revision и истории; старые попытки должны ссылаться на то условие, которое человек действительно видел. Личный прогресс пользователя не смешивается с редакторским статусом материала.

Агент — поздний слой над этой базой. Предлагаемый цикл: вопрос EN → уточнение ограничений → собственная попытка → дозированная подсказка → проверка кода/рассуждения → разбор EN/RU со ссылкой на проверенный материал → follow-up → запись попытки. Уровень языка оценивается отдельно от технической правильности.

Агент не должен бесконтрольно заменять проверенные ответы свежими догадками или оценивать правильность по совпадению слов. Версия Go и источники входят в контекст задачи. Для coding нужна отдельная ограниченная среда исполнения с квотами и таймаутом, без секретов и доступа к основной БД. API-ключ модели хранится на сервере. До подключения выбираются набор эталонных задач и критерии: корректность, неподдержанные утверждения, преждевременная выдача решения, обработка разумной альтернативы и отказ признать неоднозначность.

Сначала достаточно экспортируемого журнала попыток и ручной рубрики. Это создаёт основу и для SRS, и для будущего агента, независимо от будущего провайдера.
