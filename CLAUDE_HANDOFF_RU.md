### Стиль ответов карточек (его требования, обязательны)

## 5. Озвучка: как пользоваться

- **Локально на Mac пользователя** (v94): Kokoro стоит в `.tts/venv` (Python 3.12, `uv venv -p 3.12 .tts/venv && uv pip install -p .tts/venv/bin/python kokoro-onnx soundfile`), модель — в `.tts/`, ffmpeg из Homebrew. Генератор зовёт `python3` из PATH: `PATH=$PWD/.tts/venv/bin:$PATH node scripts/gen-audio.mjs …`. Рабочему дереву `git worktree` — символическая ссылка `.tts` на основной клон и строка `.tts` в `.git/info/exclude` (`.tts/` в `.gitignore` ссылку не скрывает).
- **Генерация.** Команда для всего, что сейчас озвучено:

  ```
  node scripts/gen-audio.mjs --week 1 --week 2 --week 3 --week 4 --cards c2,c7,c28,c29,c47,c13,c14,c15,c16,c17,c18,c19,c20,c21,c22,c23,c24,c25,c26,c27,c55,c56,c57,c58,c59,c60,c61,c62,c63,c64,c65,c66,c67,c68,c69,c70,c71,c72 [--dry-run] [--prune]
  ```

  `--dry-run` показывает текст для речи. Генерируются только недостающие файлы — около 30 секунд на файл. С v91 запись с переименованным ключом (`plan:<id>` после перенумерации) остаётся под старым именем файла и не пересоздаётся: совпадают голос и хеш речи. Запускать в фоне (`run_in_background`), не через `&`.
- **Устаревшие записи.** Изменил озвученный текст — его запись устарела (`audioStale` в `check-content`). Её нужно пересоздать той же командой.
- **Правила чтения** — `scripts/speech-text.mjs`.
  - Словарь `WORDS`: GOMAXPROCS → «Go max procs», Ps → «P's», IDs → «I-D's» и др.
  - Регулярные правила: `-race` → «dash race», `I/O` → «I-O», «→» → «then», «1 ms» → «one millisecond», `-gcflags=-m`, KiB/MiB, `x := y`, `*T`, `[]T`, `pkg.Name` → «pkg dot Name».
  - Хеш записи считается от экранного текста. Если поменялось только правило чтения, файл нужно удалить вручную и запустить генерацию снова.
- **Точечные правки** — `SPEECH_FIXES` в `scripts/gen-audio.mjs`, по ключу. Если правка перестала совпадать с текстом, генератор падает с ошибкой — значит, её надо обновить.
- **Проверка произношения.** `python3 -c "from kokoro_onnx.tokenizer import Tokenizer; print(Tokenizer().phonemize('текст','en-us'))"`. Заглавные буквы подряд синтезатор читает по буквам; слова в смешанном регистре — словами.
- **Чек-лист прослушивания.** `node scripts/audio-review.mjs` пересобирает `docs/AUDIO_REVIEW_RU.md`: все записи с длительностью, рискованные места наверху (словарь `RISK` в скрипте). Нужен ffprobe.
- **Покрытие:** c57–c64 и c66–c72 (short и jvm) — v83; c65 — v80, по ссылке из недели 1. На v75: неделя 1 — 25/25, неделя 2 — 31/31, неделя 3 — 41/41, плюс отдельно c13–c27, c28, c29, c47, c55, c56. Недели 4–13 не озвучены. На слух пользователь записи ещё не принимал.

## 6. Как я делаю каждую порцию (порядок, который хорошо работал)

1. **Ветка** `claude/<тема>` от свежего `main`.
2. **Правки данных** — скриптом, а не руками.
   - `scripts/item-edit.cjs`: `editItems(file, {id: obj => …})` и `swap(obj, key, from, to)`. swap требует ровно одно вхождение; блок пишется обратно, только если исходный блок совпал при обратном преобразовании.
   - Новые диаграммы — генератором с функциями `lane()` и `g()`; пример — v74 в журнале.
3. **Go-код** карточек и quiz выполнять на 1.24.7 и 1.27.3, где уместно — с `-race` и `go vet`. Вывод в тексты брать из реальных запусков. Для конкурентного кода запускать много раз. Код, который должен работать на 1.24, не может использовать `wg.Go` (это 1.25).
4. **Независимая проверка точности** отдельным агентом: дать ему пути, исходники Go (`/root/sdk/go1.27.3/src`) и попросить список «серьёзность, место, цитата, исправление». Исправлять всё, что подтвердилось. Каждый раз он что-то находит.
5. **Озвучка** изменённого и нового, проверка фонем у рискованных слов.
6. **Проверки:**
   - `node scripts/check-content.mjs --base origin/main` — нужно 0 ошибок и audioStale 0;
   - `node --test scripts/check-content.test.mjs` (50/50);
   - браузерные наборы `docs/verification/browser/` (README там же);
   - скриншоты 1280 и 390 px новых экранов — посмотреть самому.
7. **Выпуск:**
   - поднять `?v=N` в `index.html`;
   - добавить запись в `CLAUDE_CHANGE_LOG_RU.md` (поля: Статус, Повод, Стало…, Проверка, Ограничения);
   - коммит, push, PR через REST, merge;
   - дождаться публикации Pages и дать пользователю ссылки на новые экраны.
8. **Если пользователь «не видит» новое**, причина почти всегда в старой открытой вкладке. На сайте есть баннер обновления и подпись версии внизу каждой страницы — пусть сверит номер.

## 9. Грабли, на которые уже наступали

- `String.prototype.replace(строка, строка)` понимает в строке замены `$'`, `$&`, `$1`: текст справки с `-run='^$'` вставил вместо себя хвост файла. Данные вставлять функцией — `replace(old, () => text)` (v94).
- Фаззер Go не перебирает всё пространство `int`: мутант «`Div` через `float64`» (ошибка только после 2^53) за 30 с не нашёлся. Для демонстрации фаззинга — ошибка рядом с затравками: знак, ноль, граница (v94, `docs/verification/v94/`).
- `pkill -f serve.py…` в команде, где та же строка встречается ещё раз, убивает собственный шелл (exit 144). Использовать `pkill -f "[s]erve.py 876"`.

- Под `-race` рантайм не печатает «all goroutines are asleep»: программа просто висит. Учитывать в quiz.
- Ревью других систем часто опираются на старую версию сайта (48 карточек, старые первые фразы). Сначала сверять с текущим `main`.

- Публикация Pages иногда стоит в очереди GitHub 10–15 минут — это не ошибка.
- В Chrome у элемента внутри закрытого `<details>` `offsetParent` не null — видимость проверять `checkVisibility()`.
- Баннер «Сегодня» на плане зависит от даты (в воскресенье — «резервный день» и другая ссылка): браузерный тест может упасть только в определённый день. Фиксированное время — `page.clock`.

- `testing/synctest`: время в пузыре идёт, только пока жива его главная горутина. Горутина, которая ещё спит после её выхода, роняет тест так же, как зависшая навсегда («main bubble goroutine has exited but blocked goroutines remain»), поэтому в конце теста нужно досыпать дольше работы (в 1.27 — `synctest.Sleep`). Роняет он только «прочную» блокировку (канал пузыря, `select`, `sync.Cond`, `WaitGroup`, `time.Sleep`); зависание на `sync.Mutex` или вводе-выводе вешает тест до `-timeout`. Паника `synctest` роняет весь тестовый бинарник: демонстрации утечек запускать по одной (`docs/verification/v86/channels_checks.py`).
- Таймеры и переменная цикла зависят от директивы `go` в go.mod, а не от тулчейна: модуль с `go 1.21` получает старую переменную цикла на любом Go и старый таймер на 1.23–1.26. В Go 1.27 GODEBUG `asynctimerchan` удалён — новые таймеры у всех, `asynctimerchan=1` роняет программу при старте.
- Ссылки треков: `k2` — блок (только переход), `k2-5` — ката (даёт ✓ по отметке задачи плана). Регулярные выражения различают их по дефису: `/^k\d+$/` и `/^k\d+-/`.

Диапазон, начинающийся с недели 1 («недель 1–2»), правило не решает — правка руками. В браузерных наборах номер недели в календаре зависит от даты, а не от содержания: «сейчас неделя 3» при старте 09.11 и дате 25.11 не меняется — такие места маппер ломает, их правят руками (`check-calendar`, `check-plan`).

- После «Объединить» страница не перезагружается (v92): раздел, который держит прогресс в памяти, должен перечитывать его по событию `storage` с `key === null`, иначе после слияния покажет старое. Браузерный тест, ждущий перезагрузку после «Объединить», зависнет — ждать статус «Прогресс объединён с сервером».
- На странице задачи практикума `.practice-copy-status[role=status]` есть и у кнопок копирования файлов: статус проверки на сервере искать внутри её секции (`#practice-solution-<id>` → `.practice-section` → `p.practice-copy-status`), иначе тест читает пустую строку (v93).
- `hashchange` приходит отдельной задачей после смены `location.hash`: в браузерном тесте ждать результат перехода (нужный заголовок отрисован, фокус на нём), а не только новый hash (v93).
