**1. Правила точности**

Основной учебный ориентир — Go 1.26, с явными отличиями от 1.25 и историческими вставками, где они полезны. Факты о runtime проверялись по официальным исходникам тега `go1.25.0`; современная семантика дополнительно проверялась небольшими примерами на Go 1.26.1 darwin/arm64. Отличия 1.26 сверены с release notes и локальными исходниками установленного toolchain. Исторические утверждения — с официальными тегами/документацией, без запуска старых toolchain.

Пометки в реестре:

- **Исправить** — найдено ошибочное утверждение, неверная предпосылка или существенная пропущенная оговорка.
- **Уточнить** — основная идея полезна, но объяснение чрезмерно категорично, зависит от платформы или не подтверждает заявленную производительность.
- **Сохранить основу** — основной учебный вывод верен; предлагается улучшение формы/границ. Это не сертификат точности каждого слова.

Для каждого материала требуется различать: контракт языка/API, реализацию конкретной версии, учебное упрощение, измеренный результат. `amd64`, `arm64`, 32/64-bit и Linux-специфику обозначать явно. Слова «всегда» и «гарантирует» оставлять только там, где есть соответствующий контракт.

**6. Что различать между версиями**

Версионность не ограничивается номером установленного компилятора. У задачи могут иметь значение `go` directive в `go.mod`, `GOOS/GOARCH`, `GODEBUG`, `GOEXPERIMENT` и версия внешнего модуля. Их нужно фиксировать в воспроизводимом примере.

| Тема | Раньше | Go 1.25 | Go 1.26 | Как спрашивать на интервью |
|---|---|---|---|---|
| Переменная цикла | До language 1.22 объявленная через `:=` переменная переиспользовалась | Новая переменная на итерацию при современных language settings | То же основное правило | Какие значения возможны и почему Sleep не доказывает завершение? Что меняет `=`? |
| Рост slice | В 1.17 порог oldCap 1024, далее прибавление четверти до округления | Плавный переход с threshold 256 | Не превращать формулу в контракт | Гарантировано ли конкретное cap после append? |
| Map | До 1.24 classic buckets/overflow/evacuation | Swiss Tables | Swiss Tables, детали проверяются по тегу | Что изменилось в реализации, а какие гарантии map остались прежними? |
| Timer channels/GC | До новых semantics 1.23 недостижимые незавершённые timers удерживались runtime; другие Stop/Reset правила | Современные semantics с учётом go.mod/GODEBUG | Сохранять оговорки совместимости | Может ли GC собрать timer? Когда нужно переиспользование и как делать Reset? |
| GC — Green Tea | Ранее другая организация обхода | Эксперимент `GOEXPERIMENT=greenteagc` | Включён по умолчанию | Что меняется в организации scanning и locality, а что не делает GC generational/compacting? |
| Динамический make slice | Старые compiler limitations чаще приводили к heap | Ограничения определяются компилятором и контекстом | Stack allocation возможна в большем числе случаев | Как проверить конкретный пример, а не угадать по `make([]T,n)`? |
| GOMAXPROCS в контейнере | Обычно default от доступных CPU; часто отдельная настройка quota | Нативный учёт CPU bandwidth cgroup на Linux и динамическое обновление | Современное поведение сохраняется | Как влияет явная установка GOMAXPROCS и что такое quota vs affinity? |
| WaitGroup | Add перед go + Done | Появляется WaitGroup.Go; обновляется внутреннее состояние | API используется и дальше | Что упрощает Go, каких ошибок он не исправляет, почему f не должна panic? |
| synctest | Не существовал в 1.17; в 1.24 эксперимент | Стабильный Test/Wait | Проверять контракт именно 1.26, не переносить будущие API | Какие блокировки durable и почему Mutex не в списке? |
| Leak diagnostics | Goroutine profiles/trace, тестовые проверки | Обычные средства диагностики | Эксперимент `goroutineleakprofile` | Что способен обнаружить профиль, чего не доказывает отсутствие находок? |
| Unique/weak/cleanup | Не существовали в 1.17 | unique с 1.23, weak/AddCleanup с 1.24 | Сохранять точные контракты и версии | Почему cleanup не заменяет явное освобождение ресурса? |

Источники исторического роста: [slice.go Go 1.17](https://github.com/golang/go/blob/go1.17/src/runtime/slice.go), [slice.go Go 1.25](https://github.com/golang/go/blob/go1.25.0/src/runtime/slice.go). Остальные переходы: [Go 1.23 release notes](https://go.dev/doc/go1.23), [Go 1.25 release notes](https://go.dev/doc/go1.25), [Go 1.26 release notes](https://go.dev/doc/go1.26), [Green Tea — объяснение разработчиков](https://go.dev/blog/greenteagc).

Для 1.25 vs 1.26 обязательно выделить три изменения: статус Green Tea, расширение stack allocation слайсов, экспериментальный профиль утечек. Это не повод объявлять все сведения о tri-color GC устаревшими: базовое объяснение достижимости и concurrent mark/sweep остаётся полезным, но устройство очередей сканирования нужно версионировать.

Исторические snippets не должны случайно использовать более новые API: в Go 1.17 нет generics, `any`, типизированных atomic-обёрток, `context.WithoutCancel`, `errors.Join`, `WaitGroup.Go`, `iter` и других последующих добавлений. Для исторической демонстрации включать только нужное отличие, а не портировать назад весь курс. Регистровые и ABI-примеры тоже помечать архитектурой: изменения в amd64 нельзя автоматически переносить на arm64.

**7. Что считать проверенным перед публикацией новой редакции**

Для runnable-примера: полный файл/модуль, явно заданная версия, необходимые imports и типы; отсутствие Sleep как доказательства синхронизации; проверяемое ожидаемое поведение. Для intentional bug: отдельный режим запуска, ограничение времени и ресурсов; для race — детектор на выполненном сценарии; для deadlock/panic — subprocess, не подвешивающий весь набор тестов. Для pseudocode: явная подпись и отсутствие обещания компилируемости.

Каждой задаче нужен не только правильный вариант, но и объяснение, при каких предпосылках он правильный, почему другие варианты неверны, минимальное исправление и один follow-up. Статистику длины/позиции ответов проверять автоматически как редакционный сигнал, а качество distractors оценивать вручную.

Для source-level материалов фиксировать ссылку на tag/commit, а не только путь `runtime/proc.go`. Наличие ссылки не заменяет проверку соответствующего участка. В статье должны совпадать времена, гарантии и исключения на обоих языках. Русская формулировка «может» не должна превращаться в английское “always”.

Для production-историй: либо воспроизводимая лабораторная ситуация, либо опубликованный первичный разбор. Неподтверждённый сценарий маркировать учебным; произвольные цифры p99, RAM и ускорения не выдавать за измерения.
