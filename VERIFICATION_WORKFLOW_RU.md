# Проверка и завершение порции

Цель — убрать повторную работу, сохранив проверку технической точности и поведения сайта. Сокращение времени не считается доказанным, пока его не измерили. Нулевой риск регрессий обещать нельзя; при неясном влиянии изменений проверку расширяем.

## 1. До правок: зафиксировать периметр

Одна ветка от подтверждённого main, одна тематическая порция. Записать base, затрагиваемые ID, связанные карточки/quiz/схемы, риски и выбранные проверки. Прочитать актуальный статус и относящиеся к теме записи, не перечитывать весь исторический аудит без причины. Изменения пользователя и независимые задачи не смешивать.

| Что меняется | Обязательная проверка |
|---|---|
| Только документы | Смысл, ссылки, актуальность ID/чисел, diff; браузер и Go не нужны |
| Карточки, quiz, шаги схем, шпаргалка | Структура всего корпуса; первичные источники; EN/RU и связанные материалы; затронутые Go-примеры; общий smoke и целевой браузерный прогон |
| HTML/CSS/renderer/фильтры/навигация | Структура + широкий браузерный прогон всех затронутых типов представлений и общих сценариев |
| Storage, импорт/экспорт, календарь | Предыдущее + совместимость старых записей, reload, corrupt/blocked storage, отмена/ошибки и границы данных/дат |
| Проверяющий инструмент | Положительные и отрицательные случаи, ошибки CLI, сравнение с реальным diff; его успешный вывод не заменяет проверки сайта |

Правка только `?v=` при неизменной структуре HTML не требует заново проверять всю навигацию: нужны загрузка ресурсов и smoke. Изменение данных может влиять на фильтры, размеры и поиск; это не основание пропускать браузер полностью. Новый тип данных, непонятная связь или найденная общая регрессия переводят порцию в широкий режим.

## 2. Быстрая автоматическая проверка

Из корня репозитория, без npm и дополнительных зависимостей:

```bash
node scripts/check-content.mjs --base <base-commit>
```

Проверяются синтаксис четырёх JS-файлов, основные поля, уникальность ID, существование объявленных ссылок, границы правильного ответа quiz, комплектность добавленных EN/RU-полей и практики. Сравнение данных с base показывает изменённые/удалённые ID, порядок и изменение шпаргалки. Удаление стабильного ID — ошибка. Команда без `--base` проверяет текущие данные без сравнения.

Это минимальный структурный валидатор, не полная schema: он не проверяет все вложенные diagram boxes, источники, `CARD_TO_SIM`, смысл переводов, соответствие счётчикам редакции или техническую правильность ответов. Пустые элементы массивов тоже ошибка. VM читает только доверенные локальные данные; это не песочница для чужого JS. Чужой patch сначала проверяется как код.

Изменил проверяющий инструмент — запусти также:

```bash
node --test scripts/check-content.test.mjs
```

Набор изменённых ID — подсказка к плану проверки, а не автоматический список всего влияния. Поиск по теме и review реального diff остаются обязательными.

## 3. Проверка содержания

- Для новых/изменённых фактов использовать спецификацию, документацию API и исходники с тегом. Уже прочитанный неизменившийся tagged source можно переиспользовать с указанием версии и прежнего основания. Новый вывод, новая версия или противоречие требуют нового чтения. Текущую документацию нельзя молча считать документацией старой версии.
- Сверить EN/RU: одинаковые условия, оговорки и ответ; естественное начало; сначала собственная попытка, затем разбор. Проверить связанные материалы, не закрывая их полную редакцию за одну исправленную строку.
- Исполнить изменённые примеры с подходящим окружением: gofmt, test, vet; race для конкурентных примеров. Проверить нужные ошибки и завершение, а не только happy path. Невыполняемый псевдокод явно пометить. Не запускать все прежние Go-fixtures ради неизменённого примера.
- Assembly, escape diagnostics, benchmem и несколько toolchain нужны, когда ими обосновывается конкретное утверждение. Не добавлять их ритуально. Тест результата не доказывает устройство GC или точную трассу планировщика.

## 4. Браузер: smoke + затронутые сценарии

**Общий smoke для изменений сайта:** загрузить пять разделов; проверить ошибки и нужные ресурсы; открыть карточку, раскрыть ответ, отметить повторение и проверить отметку после reload; открыть quiz и шаг схемы. Это небольшой постоянный набор, не повторение всех прежних тематических проверок.

Для него сохранён `scripts/browser-smoke.mjs` (Node с глобальными fetch/WebSocket, проверено на Node 22.10.0). Сначала запусти HTTP-сервер по инструкции README и отдельный Chrome с `--remote-debugging-port=9228 --user-data-dir=<временный-каталог>`. Затем:

```bash
node scripts/browser-smoke.mjs --output /tmp/go-prep-smoke.json
```

Скрипт создаёт отдельный временный browser context, проверяет раскрытие ответа с клавиатуры, фокус, сохранение прогресса, базовый quiz/шаг, пять маршрутов на четырёх ширинах и загрузку ресурсов. Контекст удаляется и при ошибке; личный прогресс браузера не используется. Флаги `--url` и `--cdp` меняют адрес сайта и DevTools. `--output` необязателен, JSON также печатается в stdout; ошибка даёт ненулевой exit code. Скрипт не запускает/не останавливает сам HTTP-сервер и Chrome. Он не проверяет все состояния, перевод, визуальное качество, 200% текста или семантику Go: целевые и широкие проверки остаются отдельными.

**Целевой прогон для контента:** все затронутые ID и связанные переходы; EN/RU, код, источники, раскрытие практики, правильный/неправильный ответ quiz и навигация изменённой схемы. Сохранить прежние ширины **320/390/430/1440 px**, увеличение текста 200%, клавиатуру и видимый фокус. Не перемножать каждую смысловую проверку на каждую ширину: содержание/состояние проверить один раз, layout затронутых состояний — на всех ширинах. Исключение: поведение меняется от breakpoint, тогда проверять и его в соответствующих режимах.

**Широкий прогон:** дополнительно фильтры/поиск и пустые результаты, Back/Forward, прямые ссылки и сброс фильтра, storage failure/corruption, reset cancel/confirm, совместимость прогресса, все представления общего изменённого renderer. Проверять все состояния, на которые может влиять общий код. Нельзя объявлять его пройденным по одному smoke.

Ждать готовности страницы/DOM по условию с timeout, а не произвольными Sleep. Скриншоты делать для изменённых визуальных состояний и найденных ошибок; снимок должен быть действительно просмотрен. Не переснимать все старые темы. Использовать отдельный профиль браузера, не трогать личный прогресс пользователя. Остановить запущенный сервер и браузер после работы.

## 5. Один цикл завершения

1. Успешные проверки относятся к точным файлам/fixtures и условиям. После исправления повторить упавшие и затронутые проверки; после изменения только журнала повторять браузер незачем. При новом риске расширить набор.
2. Обновить **CURRENT_STATUS_RU.md** и **CHANGE_LOG_RU.md**. Остальные документы менять по смыслу: README — поведение/команды, аудит — новые находки/изменившиеся выводы, ответ Claude — изменения передаваемого задания. Не копировать текущие числа в каждый документ; ссылаться на статус. Исторические числа сохранять как историю.
3. Короткий отчёт: base, scope, выбранный режим и почему; реально выполненные команды/результаты; версии; новые доказательства/fixtures; ограничения. Ссылаться на предыдущие неизменившиеся доказательства вместо копирования сотен имён успешных проверок. Не перезаписывать старые отчёты и не выдавать их за новый запуск. Необходимый для воспроизведения fixture сохранять в репозитории или отчёте, а не только в `/tmp`.
4. `git diff --check`, review итогового diff и остатка, один разрешённый локальный коммит. Push/merge — по установленной договорённости с пользователем. Архив для Claude пересобирать при передаче, не после каждого внутреннего шага.

Нет обязательного второго «заключительного полного прогона» после уже успешного. Число assertions не метрика качества: в порции 9 было 994 браузерных проверки, но структурная проверка всё равно обнаружила пропущенную пустую ячейку массива шпаргалки.

## 6. После merge: проверка публикации

Подтвердить merge и сравнить опубликованные HTML/CSS/JS с ожидаемым commit, затем выполнить smoke живого сайта и открыть затронутую тему. **Совпадение байтов позволяет переиспользовать локальные смысловые тесты**, но не отменяет браузерную проверку загрузки/путей/кеша на GitHub Pages. Несовпадение, ошибка загрузки или новая среда — сначала выяснить причину, затем повторить нужные проверки. Мерж и успешная публикация — разные статусы.

Не запускать автоматически весь предыдущий набор Go/браузерных проверок онлайн. Сохранять краткое подтверждение версии, файлов и smoke; не переносить прежний счётчик проверок как будто они только что выполнены.
